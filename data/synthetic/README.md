# Synthetic data

All files in this folder are synthetic data generated for illustration. No company, customer, person, or project is represented, and no value is a measured result, a benchmark, or a record of historical use. The data is an illustrative example of the workbook in use.

## Where it comes from

| Folder | Contents | Owner |
|---|---|---|
| `r1/` | Byte-identical copies of the R1 synthetic data set at the pinned commit (3 projects, 15 phases, 12 milestones, 30 tasks, 8 requests, 6 risks, 5 issues, 18 readiness rows, 38 events) | R1 |
| `r3/` | Capacity-input definitions (35 rows): the only record-level synthetic data R3 adds | R3 |
| `manifest.yaml` | For every R1 input: source repository, source commit, source path, local path, SHA-256, and row count | generated by `tools/sync_r1_contracts.py` |

The workbook also uses R1's two complete gate-assessment and handoff records, which R1 publishes as its schema examples (`schemas/r1/schemas/gate-assessment.schema.json`, `handoff.schema.json`). Lookup entries are derived from the pinned R1 files at build time, and workbook metadata comes from `config/workbook-settings.yaml`.

## Rules

- R3 never invents a second set of projects. Synthetic Projects A, B, and C and every R1 ID are preserved.
- `tools/validate.py` fails if any file in `r1/` drifts from its pinned SHA-256 (check R05).
- To change the R1 data, change R1, then re-sync from an explicit commit.
